# モデル取得の再開・分割GGUF・キャッシュ管理

GGUFの取得はHugging FaceのファイルURLから行います。取得の開始時にリポジトリのメタデータを読み、URLのrevisionを正確な40桁のコミットへ固定します。必要なパートのファイル名・サイズ・SHA-256をまとめた情報から保存先を決めます。mainの内容や検証情報が変わった場合は別の保存先となり、古い部分ファイルは流用しません。

## 中断したGGUFの再開

同じURLからもう一度「Hugging Faceから取得」を実行してください。部分ファイルは `models/gguf-<識別子>.partial/` に残ります。新しい取得処理でも、ディスク上の部分ファイルから再開できます。

各ファイルのHEAD応答でサイズと強いETagを確認します。以前のETagと一致する場合だけ `Range: bytes=取得量-` と `If-Range` を送ります。206応答のContent-Range・ETagを検証して追記します。ETagが変わった場合・強いETagがない場合はそのファイルを最初から取得します。サーバーがRangeを無視して200を返した場合も、追記せずファイルを初期化します。エラー応答本文や署名付き転送URL、トークンは保存しません。

取得した各ファイルはサイズ・SHA-256・GGUF v2/v3ヘッダーを検証します。不一致のパートは破棄します。通信中断・キャンセルでは次回の再開用に残します。GGUFの通信待ちはキャンセル可能で、接続待ち20秒・読み込み待ち30秒、全体の上限は24時間です。

配布メタデータのLFS SHA-256を使用します。単一GGUFでSHA-256が取得できない場合は配布元の値を入力できますが、サイズとコミット情報は必要です。SHA-1をSHA-256として扱いません。取得全体の初期上限は64 GiBです。

## 分割GGUF

`model-00001-of-00002.gguf` のような先頭パートのURLを指定してください。2〜1,024パートの5桁番号形式に対応します。同じディレクトリ・同じコミットに属する全パートがメタデータにあることと、各パートのサイズ・SHA-256を必須にします。分割GGUFでは単一ファイル用のSHA-256欄を空にします。

全パートを検証し、完了情報 `manifest.json` を保存してからディレクトリを `models/gguf-<識別子>/` へ移します。全パートが揃うまでは読み込めません。読み込み時にも管理対象の全パートのサイズ・SHA-256を検証します。取得途中のディレクトリや、欠けた分割GGUFは拒否します。

自分で用意した分割GGUFでは全パートを同じフォルダへ置き、00001を選択します。全パートの存在とヘッダーは確認しますが、配布元のmanifestがないファイルのハッシュ保証はありません。モデルの解釈とアーキテクチャ対応はllama.cppが担当します。

## 空き容量とTransformers

GGUFは取得前に残量と64 MiBの余裕を確認し、パートを取得する直前にも再確認します。サイズ上限を超える場合は重みの取得を開始しません。同時に他のアプリが容量を使用することによる保存失敗はエラーとして表示します。

Transformersは既存のhuggingface_hubの再開機構を使い、必要な全ファイルを同じコミットから取得してハッシュ検証します。取得前の空き容量判定は保守的に全snapshotサイズと64 MiBを必要とします。既存blobがあっても空き容量判定では差し引きません。

## キャッシュ一覧と削除

GUIの「設定 → ローカルAI → モデルキャッシュ」で一覧を更新します。GGUF・部分取得・Transformersリポジトリごとの容量、ファイル数、空き容量を表示します。「削除する対象を確認」でパスとファイル一覧を確認してから削除します。確認後にファイルが変わった場合は拒否します。削除はアプリから元に戻せません。

Transformersの削除単位は `huggingface/models--owner--repo` 全体です。複数revisionで共有するblobとsnapshotをまとめて表示し、同じリポジトリの全revisionを削除します。シンボリックリンクはたどらず、参照先を二重計上しません。`snapshotあり` はconfigと重みの参照が見つかった意味で、ロード成功や全ファイルの再検証を表すものではありません。

取得・削除にはキャッシュ全体の排他ロック、管理対象のモデルの読み込みから推論エンジン終了までは共有ロックを使用します。別のCodeBotプロセスからも使用中の取得・削除を拒否します。保守的に、別モデルを使っている間もキャッシュ全体の取得・削除を止めます。一覧の使用中表示は更新時点の状態で、削除実行時にもロックを取り直します。OSがロックを管理するため、以前のPIDを指定してプロセスを終了することはありません。

アプリ以外のHugging Faceクライアントや推論エンジンはこのロックに参加しません。強制終了で残った外部プロセスも含め、それらを使用している場合は終了してから削除してください。通常のアプリ停止時はアプリが起動したエンジンを終了してロックを解放します。

管理対象は新しい `gguf-<64桁>` ディレクトリ、同名の `.partial`、従来の64桁ハッシュ名のGGUF/部分ファイル、Hugging Faceリポジトリです。通常のローカルパスのファイル、キャッシュ内の任意のユーザーファイル、同梱Pythonランタイムは削除対象にしません。従来のハッシュ名のGGUFも引き続きローカルパスで使えます。新方式への自動移動はありません。

一覧の上限は管理対象2,000件・合計100,000ファイル、階層64です。容量は通常ファイルの論理サイズの合計で、ファイルシステムの圧縮・疎ファイル・管理領域を含む実使用量とは異なります。GUIの削除プレビューは先頭200ファイルを表示し、全一覧はCLIで取得できます。

```sh
codebot-cli --cache-list
codebot-cli --cache-delete '一覧のid' --cache-preview
codebot-cli --cache-delete '一覧のid'
```

通常はOS標準キャッシュを使います。`--cache-dir /absolute/path` で別のCodeBotキャッシュを選べます。削除時には `delete` と入力して確認し、`--yes`はその確認を明示的に省略します。管理対象以外のIDと親ディレクトリへ抜けるIDは拒否します。削除途中にOSのエラーが発生した場合は一覧を更新してください。

## 検証範囲

ローカル模擬HTTPで別プロセスが中断した取得のディスク状態からの再開、ETag変更、200へのフォールバック、不正Content-Range、コミット変更、分割パートの欠損、サイズ/SHA-256不一致、通信待ちのキャンセルとロック解放を検証しています。キャッシュは共有/排他ロック、模擬推論エンジン存続中の保護と終了後の解放、確認後の変更拒否、外部へのリンクをたどらない削除、未選択ファイルの保持をテストしました。Pythonでは空き容量不足時にダウンロードを始めないことを確認しました。Linux実GUI/CLIで一覧・確認付き削除・未選択ファイルの保持・別プロセス使用中の削除拒否を確認しています。

Hugging Faceへの実通信、学習済みの分割GGUFによる推論、Windows/macOSの実動作は未検証です。モデル名の公式配布元と互換性の確認はCB-006、他OSでの実画面検証はCB-016で追跡します。
