## 1. 概要

OSS CodeBot
は、オープンソース開発を支援するための拡張可能な開発支援Botを目指す。

Rustで実装し、CLIとデスクトップGUIの両方から利用できる開発支援Botとする。GUI・CLIともにWindows・macOS・Linuxを対象とし、処理と設定を共通化する。AIサービスや対象ユーザーなどの未決定事項は、今後具体化する。

本書は設計仕様であり、実装済み・各OSで動作確認済みであることを意味しない。

### 1.1 コンセプト

**「開発者の面倒な作業を減らし、コードを書く・理解する・改善する作業を支援する」**

### 1.2 想定する主な機能

-   ソースコードの生成・説明・修正案の提示
-   コードレビューと品質改善の支援
-   エラーやログの解析支援
-   Gitリポジトリとの連携
-   開発タスクの自動化
-   プラグインによる機能追加

これらは候補機能であり、すべてを初期リリースに含めるものではない。

------------------------------------------------------------------------

## 2. 目的と目標

### 2.1 目的

1.  開発者が日常的に行う反復作業を減らす。
2.  コードの理解・修正・改善を支援する。
3.  OSSとして誰でも利用・改良・拡張できる構成を目指す。
4.  将来的に複数のAIモデルや外部サービスを切り替えられるようにする。

### 2.2 初期目標（MVP）

最初のバージョンでは、次の機能に絞る。

-   ユーザーからのテキスト入力を受け取る
-   AIまたはルールベースの処理を実行する
-   結果を分かりやすく返す
-   設定を外部ファイルから読み込む
-   ログを記録する
-   AI接続やBot機能を後から差し替えられる構造にする

### 2.3 初期段階では実装しない機能

-   自動で本番環境へコードをデプロイする機能
-   ユーザーの承認なしにリポジトリへ変更を反映する機能
-   複数ユーザーの権限管理を伴う大規模な管理機能
-   複雑な自律エージェント機能

必要性と安全性を検証したうえで、将来の候補として扱う。

## 4. 機能要件

### 4.1 基本機能

  -----------------------------------------------------------------------------------------------
  ID                機能                 優先度            概要
  ----------------- -------------------- ----------------- --------------------------------------
  FR-001            入力受付             必須              ユーザーの指示や質問を受け取る

  FR-002            応答生成             必須              入力に対する回答・処理結果を生成する

  FR-003            設定管理             必須              設定をコードから分離して管理する

  FR-004            ログ出力             必須              エラーや動作状況を記録する

  FR-005            エラー処理           必須              失敗時に原因を調査できる情報を出す

  FR-006            AIプロバイダー切替   将来              複数のAIサービス・モデルに対応する

  FR-007            Git連携              将来              リポジトリ、Issue、Pull
                                                           Request等と連携する

  FR-008            プラグイン           将来              機能を独立した拡張として追加する

  FR-009            コード解析           将来              ソースコードやログの解析を支援する

  FR-010            作業自動化           将来              承認を前提に開発作業を自動化する
  -----------------------------------------------------------------------------------------------

### 4.2 コード変更に関する安全要件

-   コードの変更案と実際の変更を区別する。
-   ファイルの上書き・削除・外部送信などの操作は、原則としてユーザーの確認を必要とする。
-   Git連携時は、変更内容を確認できるよう差分を提示する。
-   APIキーやアクセストークンをログに出力しない。
-   信頼できないコードを実行する場合は、隔離環境の利用を検討する。

## 6. システム構成案

初期段階では、各機能を分離したシンプルな構成を採用する。

``` text
ユーザー
  │
  ▼
インターフェース層
（CLI / デスクトップGUI：Windows・macOS・Linux）
  │
  ▼
コア処理
  ├─ 入力検証
  ├─ タスク管理
  ├─ 権限・安全性チェック
  └─ 結果・差分の整形
  │
  ├──────────────┬──────────────┐
  ▼              ▼              ▼
コード処理       GitHub連携      レビュー・解析
  │              │              │
  ▼              ▼              ▼
生成・修正・解析  Repo / Issue / PR  バグ検出・品質評価
  │              │              │
  └──────────────┴──────────────┘
                 │
                 ▼
          AIアダプター / 外部ツール
                 │
                 ▼
          ログ・設定・データ管理
```

### 6.1 設計方針

-   インターフェース層とコア処理を分離する。
-   AIサービス固有の処理をアダプターに閉じ込める。
-   外部ツールへのアクセスは、専用のインターフェースを通す。
-   将来的なCLI・Web・Discordなどの追加を妨げない構造にする。

## 7. 技術選定

開発言語はRust、提供形態はCLIとデスクトップGUI、対応OSはWindows・macOS・Linuxとする。ライブラリは以下を初期採用案とし、実装時に互換性とライセンスを確認してバージョンを固定する。

  -----------------------------------------------------------------------------------------
  分野                    候補                                 選定時の観点
  ----------------------- ------------------------------------ ----------------------------
  言語                    Rust（stable）      開発速度、実行環境、拡張性

  インターフェース        CLI: clap / GUI: egui・eframe          利用場所、ユーザー層

  AI接続                  API / ローカルモデル / 非AI処理      コスト、プライバシー、性能

  設定形式                TOML（serde・toml）                   読みやすさ、ライブラリ

  データ保存              SQLite / ファイル / 外部DB           保存量、運用規模

  テスト                  cargo test   自動テスト、保守性
  -----------------------------------------------------------------------------------------

### 7.1 技術選定の原則

1.  MVPを早く作れること。
2.  OSSとして利用・改良しやすいこと。
3.  外部サービスを必須にしない構成を検討すること。
4.  特定のAIプロバイダーに過度に依存しないこと。
5.  初期段階で不要な複雑さを持ち込まないこと。

## 9. セキュリティ・プライバシー

OSS
CodeBotはソースコードや認証情報を扱う可能性があるため、初期段階から安全性を設計に含める。

-   APIキー・トークンをソースコードに埋め込まない。
-   `.env` や秘密情報を含む設定ファイルをGitに登録しない。
-   外部サービスへ送信するデータを明示する。
-   ユーザーの許可なくファイルを削除・変更・公開しない。
-   外部から取得したコードや指示を無条件に信頼しない。
-   プラグインには必要最小限の権限だけを与える。
-   破壊的操作には確認・取り消し・バックアップを検討する。

## 13. 初期の推奨方針

現段階では、次の方針を仮採用する。

1.  **CLIとGUIを共通コアで提供する**\
    コアとCLIで処理を検証し、同じ処理を使うGUIを実装する。MVPの完了条件に両方を含める。
2.  **コア機能を小さく保つ**\
    AI接続や外部サービスを後から追加できるようにする。
3.  **AIを必須依存にしない**\
    AIが利用できない環境でも、設定確認や基本コマンドなどを動かせる設計を目指す。
4.  **安全性を優先する**\
    ファイル変更やコマンド実行は、最初は提案・確認型にする。
5.  **最初の利用目的を一つに絞る**\
    例：コード説明、GitHub管理、エラー解析のいずれか。

この方針は、プロジェクトの方向性が決まった時点で見直す。

## 16. CLI・GUI共通の実装仕様

- `codebot-core` はウィンドウや端末に依存しないライブラリとする。
- プロバイダーをtraitで抽象化し、初期版はAPIキー不要のルールベース処理を備える。AI接続は差し替え可能とする。
- CLIは引数または標準入力から指示を受け取り、結果を標準出力、診断を標準エラーへ出す。失敗時は非ゼロの終了コードを返す。
- GUIは入力欄、実行ボタン、結果欄、設定画面、処理中表示、エラー表示を備える。時間のかかる処理はバックグラウンドで実行し、UIを停止させない。
- CLI・GUIは同じTOML設定形式を使う。明示した設定パスを優先し、未指定時はOS標準のユーザー設定ディレクトリを使う。
- ログには入力本文・ソースコード・APIキーを既定で記録しない。
- 日本語を含む入力・表示を扱う。GUI用日本語フォントは再配布可能なライセンスを確認して同梱する。

## 17. ビルド・配布・完了条件

- Windows・macOS・LinuxのネイティブCIランナーでCLIとGUIをビルドし、共通コアのテストを実行する。
- CLI単独のビルドにGUIやディスプレイサーバーを要求しない。
- Linux GUIはX11・Waylandの対応と必要なシステムライブラリを確認して文書化する。
- OSごとの成果物にCLI・GUI・設定例・利用手順を含める。macOSの署名・公証、Windowsの署名、各OSのパッケージ形式は配布段階で決める。
- 各OSのGUIで起動、日本語入力、応答表示、設定読み込み、エラー表示、終了を確認する。ビルド成功だけでGUI動作確認済みとはしない。
- MVPの受入条件は、CLI・GUIで同じ入力と設定から同じ処理結果を得られ、設定不正や空入力で適切なエラーが出ること。
- 最低OSバージョンと対応CPUは未確定。検証した組み合わせをリリース時の対応表に記載する。
